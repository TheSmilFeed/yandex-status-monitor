# Что там по серверам Яндекса?

Независимый университетский проект по веб-аналитике: HTTP-доступность сервисов Яндекса и Московского Политеха, история проверок и инцидентов. Проект не является официальным сервисом этих организаций.

## Архитектура

```text
Cloudflare Cron (*/5 * * * *)
    → существующий Worker yandex-status-monitor
        → Supabase PostgreSQL (RLS включён по описанию владельца)
            → read-only API Worker
                → статический frontend → GitHub Pages
```

Production backend не изменялся. На 18.10.2026 домен и Cron подтверждены через Cloudflare Dashboard; ответы всех трёх API и CORS проверены. Исходный код Worker пока не переносился из Dashboard, SQL-схема и RLS отдельно не аудировались. Архитектура мониторинга и правила создания инцидентов основаны на переданном описании. [Подробности проверки](docs/architecture.md).

API: <https://yandex-status-monitor.fbgh111.workers.dev>.

## Запуск

Нужен Node.js 22 или новее. Внешние npm-зависимости не нужны.

```sh
node scripts/serve.mjs
```

Открыть <http://127.0.0.1:4173>. Нельзя просто открывать index.html через file://: модулям нужен HTTP-сервер. Альтернативы: `npm run dev`, `npm test`, `npm run build`, если npm установлен.

```sh
node --test
node scripts/build.mjs
```

Сборка копирует только frontend в `dist/`. Публичный URL API задаётся в `frontend/config.js`. Никакие ключи Supabase для frontend не нужны. Типографика Manrope загружается из Google Fonts; при недоступности используется системный Arial. Все значки и иллюстрации созданы в SVG/CSS, это условные значки сервисов, не официальные логотипы.

## Источники данных и мониторинг

* `/api/status`: 8 сервисов, их `current` и текущий `incident`.
* `/api/incidents`: полный доступный журнал, без угадывания связей по названиям.
* `/api/history?service=<slug>&limit=500`: последняя выборка проверок. Сервер может ограничить объём; фактическое количество показано рядом с графиком.
* Новости и состояния дата-центров пока не предоставляются публичным API. В интерфейсе показывается «Нет данных», а не вымышленные инциденты, ping или новости.
* Автоматическая проверка выполняется Worker по Cron. Кнопка «Обновить» читает результаты и не инициирует проверку.

Для Мосполитеха по текущим правилам backend три последовательных `unavailable` открывают автоматический инцидент; `operational` его закрывает. Frontend инциденты не создаёт и не закрывает. HTTP 401/403 — неопределённость. HTTP 200–399 означает доступность endpoint, а не всех функций приложения.

Для Яндекса HTTP-ошибка без внешнего подтверждения не объявляется массовым сбоем. Фронтенд учитывает `external_status`, `complaints_count` и `incident.is_confirmed`, если они реально переданы API. Ненулевое число жалоб означает внешний сигнал, а не автоматически массовый сбой. Внешние источники сейчас не подключены, значения null не заменяются нулём. Следующий этап — официальный статус Яндекс 360 и другие источники; Detector404 не является обязательной зависимостью.

Проверки старше 15 минут не показываются как актуальные. Ошибка обновления видна отдельно от состояния сервисов; последние полученные данные сохраняются только в памяти вкладки. Результаты обновляются раз в минуту, когда вкладка видима. Все даты отображаются в `Europe/Moscow`, исходные UTC timestamps не меняются.

## Страницы и графики

Главная, Яндекс, Мосполитех, История, Новости, О проекте и отдельная страница каждого сервиса. Используются hash-маршруты (`#/service/yandex-mail`) и относительные пути ресурсов: сайт работает и в корне домена, и в `/repository/` на GitHub Pages. Перезагрузка внутренних страниц не требует серверного роутинга.

График показывает только полученные измерения и разрывает линию при пропусках более 12 минут. Фильтры 24 часа / 7 дней / 30 дней / все данные относятся к загруженной выборке, а не обещают полную историю. Uptime не рассчитывается на неполной выборке. На страницах сервиса и истории доступна таблица измерений.

В текущем `/api/status` отсутствует UUID сервиса, а `/api/incidents` возвращает `service_id`, но не slug. Поэтому в карточке сервиса уверенно сопоставляется только инцидент, чей ID присутствует в `service.incident`. Не связанные события доступны в общем журнале. Для полной истории по сервису потребуется расширить API; backend ради интерфейса не изменён.

## GitHub Pages

1. Создать GitHub-репозиторий из содержимого этой папки и отправить ветку `main`.
2. В Settings → Pages выбрать **GitHub Actions** как источник.
3. Workflow `Deploy frontend to GitHub Pages` проверит данные, соберёт `dist/` и опубликует только frontend.

Workflow не имеет секретов Cloudflare/Supabase и не развёртывает backend. Настройка основана на [официальной документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages). При публикации публичного frontend нужно учитывать видимость выбранного репозитория и доступность Pages в тарифе аккаунта.

## Безопасность

Не помещать `SUPABASE_SERVICE_ROLE_KEY`, Cloudflare API tokens, `.env` или `.dev.vars` в Git и frontend. Рабочие секреты остаются в Cloudflare Dashboard. Доступ к Supabase из браузера отсутствует. API получает только GET без cookie/Authorization. Текстовые поля API экранируются, ссылки принимаются только с http(s) и без встроенных credentials. `.gitignore` исключает локальные секреты и сборку.

## Веб-аналитика

`frontend/js/analytics.js` вызывается при первой загрузке и смене страницы. Подготовлены точки регистрации адаптеров `liveinternet`, `top100`, `mailru`. Скрипты и ID пока отсутствуют. После получения настоящих ID установить официальные сниппеты, добавить адаптеры для виртуальных страниц и проверить, что одна навигация не учитывается дважды. Ошибки счётчика не должны ломать мониторинг.
